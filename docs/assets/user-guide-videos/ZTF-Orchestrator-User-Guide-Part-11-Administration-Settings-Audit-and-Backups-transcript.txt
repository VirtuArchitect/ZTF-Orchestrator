Part 11 - Administration Settings Audit and Backups
Updated 4 November 2026. Simulated console examples; synthetic narration.

Set up the correct execution runtime
Setup and Install checks prerequisites and the configured framework paths. Use the compatible legacy runtime for Workflows and Scripts one point x. Keep the separate two point x runtime and command for its preview plan and apply surface. A detected path is not proof of provider compatibility. Verify the relevant non-mutating command before allowing operational work.

Manage users and administrator sessions
Administrators create named console users with administrator, operator or viewer roles. These are Orchestrator accounts, separate from local P E accounts. Provision initial access securely and review execution permissions.

Users now includes the administrator-only Sessions panel. Signed-in users and total sessions are different counts because a user can have multiple sign-ins. Recently active means recorded interaction within five minutes. Polling and an idle open tab do not count as activity or extend expiry. Older sessions can show Not tracked.

Inspect the user, role, sign-in time, expiry and activity before revoking an individual session. Confirm the selected revocation; revoking your current session signs you out. In-flight requests may finish and durable jobs continue. Session revocation is audited and does not cancel infrastructure work.

Review runtime connections and governance settings
Settings contains runtime paths, connection profiles, governance, storage, notifications and build identity. Review a profile before using its defaults. A connection test has a specific scope and does not create target accounts or prove every A P I permission. Preserve effective trust mounts and runtime settings during updates. Review exact approval policy before enabling a sensitive lane.

Back up state and review appliance signals
Use the established backup procedure for the actual storage backend. Preserve credentials, configurations, managed cluster records, persistent review items, recovery history and required host settings. Retain database and data recovery materials independently.

Operational appliance signals now show reported application health, backup-record age, update-service availability and build identity. These help decide what to inspect. A recent backup record is not proof that a restore works, and reported build identity should be checked against the running image during support.

Test backup readability and rehearse restoration safely. Application-image rollback is separate from database restoration. Restoring Orchestrator state does not reverse changes already made on Nutanix targets. Use the actual backend recovery procedure and retain the matching evidence.

Use audit and build identity during support
Audit Log helps trace authentication, authorization, configuration, jobs and governance actions. Correlate the record with a timestamp, exact installed build and job identifier. Settings About and the running image distinguish patch builds; the footer release alone may not. Export only sanitized support evidence. Keep passwords, session tokens, private keys and secret-bearing configuration out of public reports.
